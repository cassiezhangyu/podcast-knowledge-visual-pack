# 内容处理与双重人工检查协议

本协议连接 Grounded Transcript、内容梳理、内容拆分与图片内容规划。两个内容阶段各自回答不同问题，必须顺序执行并分别获得用户确认。

## 1. 固定顺序与状态

`音频 → Grounded Transcript → 内容梳理 → 用户确认 → 内容拆分 → 用户确认 → 图片内容规划 → 逐页视觉生产`

- 不得跳过、合并或倒置两次人工检查。
- 机器检查通过后，阶段状态仍是 `needs_human_review`。
- 只有用户明确通过，才记录审批产物、输入哈希和 `accepted/pass` 状态。
- 后一阶段只能读取上一阶段已通过版本，不得读取草稿并假装完成。

## 2. 输入身份与来源边界

开始《内容梳理》前固定并记录：音频、Grounded Transcript、corrections 的路径和 SHA-256，以及本次声称处理的范围。

- Grounded Transcript 是正式内容证据；Raw Transcript 用于回查，Show Notes 只作辅助定位和专名核对。
- 若材料只覆盖片段，必须把范围写成片段，不能声称完成整期节目。
- 转写中的不确定 speaker、数字、专名或断句继续保留不确定性；内容阶段不能默默猜测。

## 3. 《内容梳理》：从原文建立全文台账

### 3.1 它回答什么

《内容梳理》回答：**播客原文实际说了什么？** 此阶段保存内容真相，不决定页面数量和画法。

### 3.2 连续覆盖

按语义边界把全部 Grounded span 划成连续片段。每个 span 必须且只能出现一次，并标记为：

- `semantic`：有论证、案例、过程、人物或反思价值；
- `context_only`：理解语境所需但不构成独立知识；
- `non_semantic`：口头重复、无语义停顿等；
- `excluded`：广告、节目公告等明确排除内容。

非语义或排除内容也要保留范围与理由，不能直接消失。检查缺口、重叠、顺序错误和没有内容单元的 semantic 片段。

### 3.3 内容单元

用“独立讨论后仍有解释价值”作为内容单元边界。每个有语义价值的单元至少保存：

- 完整但适度压缩的摘要；
- 问题、观点和归因主体；
- 论据、推理和机制；
- 案例及其中的具体人物、产品、物件、动作、数字和关键转折；
- 成立条件、反例、边界和不确定性；
- 可回查的时间戳、Grounded span 和 Raw 引用。

重复表达可以合并，但不能只留下抽象结论。判断是否过度压缩时，反问：读者是否还能知道“谁做了什么、遇到什么、为何改变、结论受什么限制”。

对核心单元再写一句**论证重心**：它主要解释哪个问题，哪条来源支持的机制使结论成立，哪些材料只是例证、旁证或边界。把这一判断与可回查的细节 ID 并列呈现；若原文只给出案例而没有解释机制，明确标为案例层，不替节目补出普遍规律。后续规划应能看出主机制与例子在论证中的不同权重。

### 3.4 语义边界

- 区分嘉宾原话、主持人总结、节目级综合和模型推断。
- 后来的理论解释不得倒写成当时的设计依据。
- 后来出现的用户用途不得倒写成最初规划。
- 个人经历、单一案例和比喻不得无条件改写为普遍规律。
- 相邻出现或主题相似不等于存在因果、递进或演化关系。

### 3.5 双向查漏

完成初稿后执行两次检查：

1. **原文 → 台账**：沿 Grounded span 顺序检查，确认每段有处置且重要细节进入内容单元。
2. **台账 → 原文**：逐项回查观点、案例、数字、归因、边界和高风险推断，确认都有证据。

机器覆盖通过只证明 span、ID 和锚点完整，不证明摘要忠实或重要细节充分。

### 3.6 用户审阅面

输出供用户阅读的 `内容梳理.md`，先给来源范围和全文骨架，再逐个呈现内容单元。每个单元包含摘要、展开、具体材料、边界和来源。末尾列出：

- 连续覆盖概览；
- 高风险归因、关系、数字和不确定性；
- 请用户优先检查的可能遗漏或误解；
- 当前停止点。

同步输出 `episode_content_inventory.json` 和 Content Review Gate。用户确认前停止，不生成《内容拆分》或页面规划。

## 4. 《内容拆分》：从全文台账重建论证结构

### 4.1 它回答什么

《内容拆分》回答：**整期在讲什么，以及怎样拆成可完整理解的模块？** 它只读取已通过的 Content Inventory，并绑定其哈希。

### 4.2 自上而下确定整体

先通读全部内容单元，再提出并比较节目级问题和主命题候选。最终主命题必须：

- 能解释核心内容，而非只覆盖节目结尾或最显眼案例；
- 是完整判断句，说明对象、机制或变化；
- 明确适用边界、反例和不能被误解成什么；
- 能容纳平行线；不能为了单一主线伪造因果。

### 4.3 确定模块边界

以独立问题、结论和论证依赖确定模块，不按固定时长、固定页数或现成版式切分。合并两个内容群前检查：

- 它们是否共同回答同一个问题；
- 是否存在来源支持的关系；
- 合并后是否仍能保留各自论据、案例和边界；
- 读者是否能说清两者在模块中的不同作用。

只有主题呼应时，可并列或设为平行线，不得写成因果链。

### 4.4 展开每个模块

每个模块至少包含：

- 模块职责、问题、结论和与前后模块的真实关系；
- 按理解顺序排列的逻辑步骤；
- 每一步的 source unit、detail 和论证功能；
- 支撑案例、具体对象、关键动作与转折；
- 条件、反例、边界和开放问题。

模块展开时检查每条核心机制是否仍在逻辑步骤的主位，案例究竟证明、限制还是仅说明它；不能只因某个案例易于绘制，就用案例代替机制。对同一方法的总图、具体操作和实际检验分别标明职责，供后续页面分配避免重复。

内容模块不是页面合同。模块数量不自动等于 Deep Dive 数量，页面合并与信息预算留给后续图片内容规划。

### 4.5 全量内容去向

为 Inventory 中每个内容单元和每个 supporting detail 记录一次处置：节目框架、某个模块、节目收束或有理由排除。处置必须说明它在目标位置承担 claim、mechanism、evidence、example、boundary、counterpoint、context 等何种作用。

检查：

- 无遗漏、无重复 disposition、无不存在的来源或模块引用；
- 每个模块的 required details 全部进入逻辑步骤；
- 降级、合并或排除有内容理由，不以页数、版式或视觉难度为理由；
- 没有把拒绝的关系重新写进模块过渡。

### 4.6 用户审阅面

输出 `内容拆分.md`，按以下顺序呈现：

1. 整期问题、主命题和边界；
2. 模块数量、拆分理由与模块关系；
3. 每个模块的完整展开；
4. 全部内容去向与合并/排除理由；
5. 需要用户重点判断的模块边界和关系；
6. 当前停止点。

同步输出 `content_split.json`、`content_split_coverage.json` 和 Content Split Review Gate。用户确认前停止，不进入图片内容规划。

## 5. 内容到视觉的交接

页面分配须先按 `rules/page_content_planning.md` 完成逐页存在性与论证深度审查，再提交图片内容规划供用户确认。覆盖矩阵只验证去向；若某页与总览或相邻页的新增理解说不清，或标题所问的主机制没有进入论证步骤，返回本阶段重排页面，不把材料留给绘图阶段补救。

图片内容规划只能读取已确认版本的《内容梳理》《内容拆分》及其机器产物，并记录：

- Content Inventory SHA-256；
- Content Split SHA-256；
- Content Split Coverage SHA-256；
- 两次 Human Review 的状态和日期。

页面合同中的每项论点、证据、案例和边界必须回指这些内容 ID。视觉可改变表达形式，不能改变内容归因、关系和成立范围。

规划稿中，总览每个 `mental_model_components` 项须给出 `model_role`（`question`、`signal`、`process`、`judgment`、`practice`、`boundary`、`new_context`、`conclusion`）；每条 `overview_relation_ledger` 须给出 `connector_kind`（`parallel_context` 或 `relationship`），多页总览时还须给出所属 `page_id`。选择 `relationship` 时还须给出 `accepted_relationship`：`from_source_id`、`to_source_id`（指向已批准的 detail 或 module）、`type`（知识图关系类型）、`direction`、`evidence_anchor_ids`。关系要有来源支持，不因主题接近就标为确定关系。新增字段须随规划提交并经用户确认，不能在审批后补填。

规划稿获用户通过后，核对规划与已批准 Inventory / Split 的哈希，运行 `npm run content:assemble -- --workspace <workspace>` 生成正式知识图、编辑规划和覆盖矩阵及门禁。此入口对缺失语义字段、多页总览中没有归属页的关系明确报错；续页进入正式 `overview_continuations`，不得擅取第一页后丢弃其他页。正式门禁只代表内容与规划获批且映射完整，不代替逐字转写人工校对。旧的 transcript-window 知识组装器不用于此流程。

## 6. 返工与失效范围

| 发现的问题 | 返回阶段 | 后续影响 |
|---|---|---|
| 转写缺失、专名或数字错误 | Transcript | 内容梳理及全部下游失效 |
| 内容单元遗漏、过度压缩、错归因、边界丢失 | 内容梳理 | 内容拆分及全部下游失效 |
| 主命题错误、模块边界不成立、关系伪造、内容无去向 | 内容拆分 | 图片内容规划及全部视觉页失效 |
| 页面漏掉已确认内容，但上游完整 | 图片内容规划 / 当前页面合同 | 只重做受影响页面及相关跨页检查 |
| 图形、文案、颜色或排版失败 | 逐页视觉生产 | 按页面视觉协议返工，不改写上游事实 |

上游内容发生语义变化时生成新哈希并重新获得相应 Human Review；不能保留旧审批状态。

具体来源、审批与覆盖判断按本规则执行；历史开发复盘不作为公共运行时前置输入。


## 转写上游检查

内容入口运行前复核当前 `grounded_transcript_qa.json`。schema、生产文本与证据哈希全部有效且技术状态为 pass 才继续覆盖和内容审阅检查。机器检查通过后仍保持 needs_human_review；技术 QA 不授予人工审批。
